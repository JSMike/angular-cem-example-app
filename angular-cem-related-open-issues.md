# Open Angular issues related to Custom Elements Manifest support

Checked against the [`angular/angular` open issue tracker](https://github.com/angular/angular/issues)
on 2026-07-26. This is a curated list of issues that overlap the proposed
`customElementsManifests` feature or define an important integration boundary. It intentionally
excludes most `@angular/elements` producer-side lifecycle, styling, and packaging bugs.

## Direct overlap or useful precedent

| Issue                                                                                                                             | Relationship to this feature                                                                                                                                                                                                                                                                                                                                                                                                                      | Suggested PR treatment                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [#36893 — Language Service: integration with custom-elements.json specification](https://github.com/angular/angular/issues/36893) | The clearest precedent. It asks for custom-element property/event completion, descriptions, and types in Angular templates. The issue demonstrates the older VS Code custom-data JSON shape rather than today's Custom Elements Manifest schema. A maintainer later preferred using `.d.ts` declarations; this implementation reconciles the two approaches by using CEM `type.references` to validate and import actual TypeScript declarations. | Treat as directly resolved and use `Closes #36893`. The PR should explain that it fulfills the requested editor experience through the modern CEM schema while validating referenced `.d.ts` declarations.                 |
| [#12045 — `[RFC]` elements schema: add support for custom schemas](https://github.com/angular/angular/issues/12045)               | Identifies the foundational problem: `CUSTOM_ELEMENTS_SCHEMA` allows every custom tag/property instead of describing known elements, properties, and events. A configured CEM is a standards-based custom schema source, though this PR does not add a general arbitrary-schema API.                                                                                                                                                              | Cross-reference as the long-running compiler/schema motivation. Do not claim the broader custom-schema request is completely solved.                                                                                       |
| [#58483 — TypeScript interface for element definitions](https://github.com/angular/angular/issues/58483)                          | Proposes an augmentable `IntrinsicElements`-style TypeScript interface for custom and built-in element definitions. CEM ingestion solves much of the same custom-element authoring experience through a different, package-published mechanism. It does not provide user augmentation for built-in elements or an arbitrary TypeScript-only escape hatch.                                                                                         | Compare the approaches in the PR design discussion. Emphasize package discovery, CEM documentation metadata, and validated `.d.ts` references; acknowledge that interface augmentation remains a separate extension point. |
| [#36355 — Angular binding DOM property instead of web component property](https://github.com/angular/angular/issues/36355)        | Reports Angular remapping a custom element's exact `readonly` property to native `readOnly`. The CEM branch directly fixes this for manifest-declared properties by preserving exact names while retaining native remapping for inherited DOM properties.                                                                                                                                                                                         | Add as concrete evidence for exact-name code generation. The issue is only fully resolved for manifest-backed elements; `CUSTOM_ELEMENTS_SCHEMA`-only usage remains unchanged.                                             |
| [#61001 — Recommended way to use web components from within an Angular app?](https://github.com/angular/angular/issues/61001)     | Requests first-class guidance and integration for loading, binding to, and handling events from web components. CEM support provides the compile-time binding/event side, but intentionally does not load component scripts, register elements, or coordinate `@defer`.                                                                                                                                                                           | Reference as broader user demand. Clearly scope the PR to compile-time integration and keep runtime loading/registration separate.                                                                                         |
| [#44110 — Support scoped custom element registries](https://github.com/angular/angular/issues/44110)                              | Scoped registries may eventually allow different definitions for the same tag in separate DOM scopes. The proposed CEM option currently describes a program-wide tag map with deterministic first-wins duplicate handling. A maintainer comment on the issue specifically notes the value of Angular having compile-time knowledge of custom-element definitions.                                                                                 | Treat as a future architecture constraint, not work for this PR. Avoid implying that the initial manifest model supports scoped or per-component registries.                                                               |

## Related integration gaps not solved by CEM ingestion

| Issue                                                                                                                         | Why it is related                                                                                                                                       | Boundary of this feature                                                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [#28491 — Namespaced custom events](https://github.com/angular/angular/issues/28491)                                          | Some web components emit valid event names containing `:`, while Angular parses `:` as a global event-target separator.                                 | A manifest can describe the event, but CEM typing cannot override Angular template parser syntax or runtime listener targeting.                                           |
| [#63174 — Support for built-in custom elements](https://github.com/angular/angular/issues/63174)                              | Customized built-ins use `<button is="custom-button">` and require `createElement` options rather than an autonomous hyphenated tag.                    | The current CEM feature models autonomous custom-element tag declarations. Supporting the `is` form requires separate compiler and runtime creation changes.              |
| [#45712 — Web-component properties are undefined inside `connectedCallback`](https://github.com/angular/angular/issues/45712) | Angular creates and attaches an element before update-mode property bindings run, so a component may observe missing values during `connectedCallback`. | Exact CEM property names improve which property is written, but do not change creation/binding order.                                                                     |
| [#63015 — Additional `ngDefaultControl`-style directives for value types](https://github.com/angular/angular/issues/63015)    | Form-associated custom elements need Angular Forms adapters for boolean, numeric, and other non-string values.                                          | CEM validates properties and events; it does not create `ControlValueAccessor` behavior or define how event payloads update a form control.                               |
| [#69232 — Signal Forms support for custom elements](https://github.com/angular/angular/issues/69232)                          | Requests native-like Signal Forms behavior for form-associated custom elements, including metadata such as `min` and `max`.                             | Manifest typing can describe these members but does not make Signal Forms recognize or coordinate the element at runtime.                                                 |
| [#48746 — Platform-server support for Shadow DOM and custom elements](https://github.com/angular/angular/issues/48746)        | Covers executing/rendering custom elements and Shadow DOM in Angular SSR's server DOM environment.                                                      | CEM ingestion is compile-time-only and has no direct SSR runtime dependency. Passing Angular SSR compilation does not supply a server-side custom-element implementation. |
| [#52275 — Client hydration for web components hydrated on the server](https://github.com/angular/angular/issues/52275)        | Server-side component transforms, such as Stencil's rendering, can change Angular's expected DOM and produce hydration mismatches.                      | CEM does not alter rendered DOM or hydration bookkeeping. This remains a runtime interoperability problem even when templates are fully typed.                            |

## Recommended cross-references when opening the PR

1. Use **Closes #36893** in the commit footer. The PR should explain that it supports the modern
   Custom Elements Manifest format and uses referenced TypeScript declarations when supplied.
2. Cite **#12045**, **#58483**, and **#36355** in the motivation/design section. Avoid `Fixes` or
   `Closes` because each has scope outside the initial CEM implementation.
3. Mention **#61001** when explaining that this PR improves compilation and editor integration but
   deliberately leaves script loading and element registration to applications and libraries.
4. Keep **#28491**, **#44110**, **#48746**, **#52275**, **#63015**, **#63174**, and **#69232** in a
   related-work or follow-up section only. They should not expand the initial PR's scope.
5. After a PR URL exists, add a concise comment to #36893 explaining the schema evolution and
   inviting verification before merge. Add non-closing comments to #12045, #58483, and #36355 so
   their authors and maintainers can evaluate the overlapping behavior.
